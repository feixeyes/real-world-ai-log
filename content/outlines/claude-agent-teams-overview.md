## 功能速览：agent teams 是什么
- 背景：Opus 4.6 发布时加入 agent teams，定位为研究预览。
- 核心卖点：多个子代理并行协作，主代理协调；1M context 支撑长任务；面向 Claude Code/API 用户。
- 期待收益：缩短长任务耗时、覆盖大体量上下文、减少人为拆解成本。

## 工作方式（原理线索）
- 角色分工：主代理负责任务拆解和协调；子代理各自有独立上下文，可相互沟通、共享待办列表。
- 与旧版 sub-agent 的差异：从单向回传升级为多向交流+依赖解锁，更像“小团队”协同。
- 长上下文的作用：1M tokens 让整仓代码、跨文档比对成为可能，但成本随之上升。

## 使用条件与开启方式
- 可用界面：Claude Code、API；需显式开启实验开关（如 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）。
- 账号要求：Team/企业版优先开放，个人订阅视控制台开关而定。
- 建议操作：先在低风险项目里打开；记录开关位置、可见性、日志获取方式。

## 成本与限制
- 计费：并行代理累计 token 开销，长上下文价格更高；需监控输入/输出 token 及并发数。
- 稳定性：研究预览阶段，可能出现协调偏移、超时或质量波动。
- 操作复杂度：任务拆分质量取决于主代理；拆分不佳会放大成本浪费。

## 适合的任务类型
- 可拆分的并行工作：安全/性能/测试多视角代码审计；多文档综述；多路数据比对。
- 高上下文长链路：整仓迁移、跨模块重构、法规/财报并行解读。
- 需要角色分工的任务：一人主导，子代理分别担任“审计”“总结”“对照”等角色。

## 不适合或需谨慎的场景
- 需求尚未成型、难以清晰拆分的探索式任务。
- 高合规/高一致性要求但缺少人工把关的场景。
- 极短小任务：并行调度成本可能高于收益。

## 首次尝试的最小方案
- 配置：开 2–3 个子代理，设置 token 上限与最大并行数；准备一键回退到单代理。
- 流程：先让主代理展示拆分结果→人工确认/微调→再允许子代理并行执行。
- 观察点：
  - 拆分是否合理、是否出现重复/冲突。
  - 子代理沟通内容是否跑偏；必要时插入人工提示纠偏。
  - 速度提升与成本比值；记录具体任务耗时与 token 账单。

## 开放问题与后续观察
- 协调质量的上限：子代理数量与任务难度的平衡点？
- 与“Summarize from here”等新控件的配合效果；是否能减少中途遗忘。
- Fast Mode 与标准模式在 agent teams 下的性价比差异。
- 什么时候需要为每个子代理明确角色提示，什么时候让主代理自定更好。
